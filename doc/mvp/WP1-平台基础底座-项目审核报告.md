## 1. 审核结论

**结论：有条件通过。**

WP1 PRD 和系统架构设计整体覆盖了总体方案中对平台基础底座的核心要求，包括多租户、多部门、多项目、多应用、用户角色、环境配置、权限隔离、敏感配置保护、操作审计，以及对后续模型接入、测试资产、输入连接器、测试数据、执行调度和企业协作连接器的上下文支撑。

当前文档已具备进入研发任务拆解的基础，但不建议直接进入全量开发。建议先完成“研发前补充事项”中的 P0 澄清与冻结，再进入 Sprint 级任务拆解和接口评审。未补齐前，权限、登录初始化、密钥管理、审计口径和前后端接口契约存在返工风险。

## 2. 范围一致性检查

### 2.1 与总体方案的一致性

总体方案要求平台从第一天按多租户、多项目、多部门建设，并为权限、数据隔离、资源配额、审计、模型策略、执行环境和企业集成提供基础能力。WP1 PRD 和架构设计与该要求基本一致。

已覆盖范围：

- 多租户作为最高数据隔离边界。
- 部门树、用户、项目、应用、环境等基础空间模型。
- RBAC + 资源作用域的权限模型。
- 环境变量、服务地址、鉴权配置、密钥引用和敏感值保护。
- 操作审计、权限拒绝审计、登录审计和后续工作包审计接入点。
- 为 WP2/WP3/WP8/WP9/WP11 提供租户、项目、应用、环境、权限和审计上下文。

### 2.2 与 WP1 范围的一致性

WP1 当前范围聚焦“平台基础底座”，未越界建设测试资产、AI Agent、执行调度、报告看板等后续工作包能力，边界总体清晰。

存在轻微越界但可接受的设计项：

- 架构设计中出现 `allow_public_model`、敏感级别、默认执行资源池、生产环境执行开关等字段。这些属于后续 WP2/WP9 的策略入口，但作为 WP1 预留字段合理。
- 环境健康检查、资源池入口、凭证引用读取等能力接近后续执行或数据能力边界。建议 WP1 只做配置与状态字段，复杂探测、调度和解密执行留给后续工作包。

存在遗漏或需明确的范围项：

- 登录方式、超级管理员初始化方式、密码策略和会话策略在 PRD 中描述偏概念，研发可执行性不足。
- “基础配额”在架构范围中出现，但 PRD 非范围声明不建设商业化资源配额，需明确 WP1 是否只保留字段。
- 项目可关联多个部门，但架构表 `base_project` 仅有单个 `dept_id`，与 PRD 表述不一致。
- 应用负责人、项目负责人支持“一个或多个”，但架构表多处仅保留单个 `owner_user_id` 或通过成员关系间接表达，需统一。

## 3. PRD 完整性检查

### 3.1 用户角色

PRD 覆盖了平台超级管理员、租户管理员、部门负责人、项目负责人、应用负责人、测试工程师、研发工程师、只读审计员等角色，基本满足 MVP 管理后台使用场景。

需补充：

- 各角色对应的菜单可见性和默认数据范围。
- 预置角色与架构中的角色命名映射，例如 `SuperAdmin` 与 `SystemAdmin`、`ProjectOwner` 与 `ProjectAdmin`、`Auditor` 与 `Viewer` 的关系。
- 部门负责人是否具备创建项目、管理部门成员、查看部门审计的权限边界。

### 3.2 用户流程

PRD 已描述租户初始化、组织与用户配置、项目与成员配置、应用与环境配置、权限变更、审计查询六条关键流程，主链路完整。

需补充：

- 首次系统初始化流程：超级管理员如何创建、是否命令行初始化、是否默认租户、初始密码如何交付。
- 登录、登出、会话过期、用户锁定、密码重置或邀请激活的流程。
- 停用租户、停用项目、停用应用、停用环境对已有成员、角色绑定和历史数据的影响规则。
- 权限不足、资源不存在、跨租户访问等异常流程。

### 3.3 功能和页面

PRD 的功能清单按租户、部门、用户、项目、应用、环境、角色权限、操作审计拆分，并标注 P0/P1/P2，具备研发拆解基础。页面信息架构也覆盖了管理后台核心页面。

需补充：

- P0 页面字段级规格，包括必填、格式、枚举、默认值、是否可编辑。
- 列表筛选、排序、分页、空状态、错误态的统一验收口径。
- 高风险操作的二次确认文案、阻断条件和可恢复方式。
- 审计导出、用户导出、配置导出是否进入 MVP P0/P1 的最终取舍。

### 3.4 权限与验收

PRD 已有权限层级、权限校验规则、敏感数据规则和验收标准，方向正确。

需补充：

- 权限矩阵：角色 x 资源 x 动作 x 作用域。
- API 权限校验清单：每个 P0 接口对应权限点、作用域来源和拒绝审计要求。
- 验收标准需要从描述性条目细化为可测试用例，至少覆盖正向、越权、停用、敏感字段脱敏、审计生成五类场景。

## 4. 架构设计完整性检查

### 4.1 模块设计

架构设计将 WP1 拆为 `iam`、`org`、`project`、`environment`、`rbac`、`audit`、`config` 等模块，并建议 MVP 由 `platform-api` 承载，符合首期降复杂度和边界清晰的要求。

需补充：

- 模块间依赖方向和事务边界，例如创建租户时角色初始化、管理员创建、审计写入的失败处理。
- 服务间鉴权方案，尤其是 WP2/WP3/WP8/WP11 调用上下文、配置和审计接口时的服务身份与用户委托关系。
- 前端路由与后端权限点的映射原则。

### 4.2 模型和表设计

核心实体和数据库草案基本完整，已覆盖租户、部门、用户、会话、项目、应用、环境、变量、配置、权限、角色、角色绑定、审计、审计 outbox。

需修正或澄清：

- `base_project` 只有 `dept_id`，但 PRD 写明项目可关联多个部门。建议增加项目部门关联表，或将 PRD 调整为 MVP 仅支持主归属部门。
- `sys_department.manager_user_id` 仅支持单负责人，但 PRD 支持多人。建议使用部门负责人关联表，或明确 MVP 单负责人。
- `base_application.owner_user_id` 仅支持单负责人，但 PRD 支持一个或多个应用负责人。建议通过成员/角色绑定表达负责人。
- `base_env_variable` 同时出现 `plain_value` 与“密钥不落明文”原则冲突。建议普通变量可明文，敏感变量必须仅存 `secret_ref` 或加密引用，并明确字段语义。
- `tenant_id` 在平台级操作可为空还是使用系统租户，两份文档口径需统一。

### 4.3 接口设计

架构设计给出了关键 API 草案，已能支持研发拆解。

需补充：

- 请求/响应 DTO、错误码、幂等策略、分页格式、排序格式、筛选参数规范。
- 创建、编辑、启停、授权类接口的审计事件编码。
- 状态变更接口的允许状态流。
- 环境变量批量更新的增量/覆盖语义。
- `/configs/effective` 的作用域参数、返回来源 `source_scope`、敏感字段返回策略。

### 4.4 安全审计

安全和审计设计较充分，包含租户隔离、权限拒绝审计、密钥引用、审计脱敏、生产环境默认关闭执行等要求，符合企业级底座定位。

需补充：

- MVP 阶段未接入 Vault/KMS 时的临时 `SecretProvider` 实现方案、加密算法、密钥轮换和迁移策略。
- 登录失败锁定策略、Token 有效期、刷新策略、会话注销和用户停用后的会话失效机制。
- 审计 outbox 的补偿、重试、告警和最终一致性验收标准。

### 4.5 扩展边界

架构对 WP2/WP3/WP4/WP5/WP8/WP9/WP10/WP11 的接口边界描述清晰，符合总体方案的控制面定位。

需补充：

- 后续工作包不得直接读写 WP1 表，应通过 API 获取上下文、配置和审计写入能力。
- 模型策略字段、执行资源字段、账号池凭证字段的 owner 工作包和生效时机。
- 配置继承冲突时的解释权和排障方式。

## 5. PRD 与架构设计的一致性问题

| 序号 | 问题 | 影响 | 建议 |
|---|---|---|---|
| 1 | PRD 预置角色为 `SuperAdmin/TenantAdmin/ProjectOwner/AppOwner/Tester/Developer/Auditor`，架构角色为 `SystemAdmin/TenantAdmin/DepartmentManager/ProjectAdmin/TestLead/Tester/Developer/Viewer` | 研发、测试和权限初始化口径不一致 | 冻结一版角色命名和映射表 |
| 2 | PRD 项目可关联多个部门，架构表仅支持单 `dept_id` | 数据模型可能无法满足产品要求 | 增加关联表或明确 MVP 仅主部门 |
| 3 | PRD 部门负责人、项目负责人、应用负责人支持多人，部分架构字段只支持单人 | 负责人授权和页面展示会返工 | 统一使用成员关系/角色绑定表达负责人 |
| 4 | PRD 环境可为项目公共环境或应用专属环境，架构 API 仅通过 `/applications/{appId}/environments` 创建环境 | 项目公共环境接口缺失 | 补充项目公共环境创建与查询接口 |
| 5 | PRD 强调敏感值加密存储，架构原则强调密钥不落明文，但表中有 `plain_value` | 安全实现口径易混乱 | 区分普通变量明文与敏感变量密钥引用，不允许敏感值明文入库 |
| 6 | PRD 非范围不建设模型路由，架构含 `allow_public_model` 等模型策略入口 | 容易扩大 WP1 研发范围 | 明确 WP1 只维护策略字段，不实现模型路由 |
| 7 | PRD 提到项目负责人，架构表/角色使用 ProjectAdmin/TestLead | 角色授权和页面文案不一致 | 统一产品角色、技术角色、预置角色编码 |

## 6. 关键风险与阻塞项

| 等级 | 风险/阻塞项 | 说明 | 处理建议 |
|---|---|---|---|
| P0 | 权限矩阵未冻结 | 没有角色 x 权限 x 作用域矩阵，后端鉴权、前端菜单和测试用例无法稳定拆解 | 研发前冻结 MVP 权限矩阵 |
| P0 | 初始化和登录方案不完整 | 超级管理员、租户管理员、邀请激活、密码与会话策略不明确 | 补充 IAM 最小闭环规格 |
| P0 | 密钥管理落地方案未定 | Vault/KMS 若暂不可用，敏感配置存储方案会阻塞环境模块 | 明确 MVP `SecretProvider` 实现与迁移路径 |
| P0 | PRD 与表结构存在多处一对多不一致 | 项目部门、负责人、公共环境等会影响数据库迁移与 API | 研发前完成模型差异决策 |
| P1 | 审计事件编码和触发点未清单化 | 审计覆盖率 100% 难以验收 | 输出 P0 审计事件清单 |
| P1 | API 契约还是草案级 | 前后端并行开发和自动化测试缺少稳定依据 | 形成 OpenAPI 或接口契约文档 |
| P1 | 配置继承规则缺少冲突处理细节 | 后续 WP2/WP9 读取配置时可能解释不一致 | 明确返回来源、覆盖规则、删除/恢复默认规则 |

## 7. 进入研发前必须补充的事项

1. 冻结 MVP 角色、权限点、菜单权限和作用域矩阵。
2. 明确超级管理员初始化、租户管理员创建、用户邀请/激活、登录、登出、会话过期、停用失效的最小流程。
3. 修正 PRD 与架构的一对多模型差异：项目-部门、部门负责人、项目负责人、应用负责人、项目公共环境。
4. 输出 P0 接口契约，至少包括请求/响应、错误码、分页、筛选、状态流、审计事件编码和权限点。
5. 明确敏感配置的 MVP 落地方案：普通变量、敏感变量、密钥引用、脱敏展示、审计脱敏、临时密钥服务。
6. 输出 P0 审计事件清单，覆盖登录、租户、组织、用户、角色、授权、项目、应用、环境、导出、越权访问。
7. 明确 `allow_public_model`、敏感级别、执行开关、资源池字段在 WP1 中仅作为配置字段，不实现后续业务逻辑。
8. 将验收标准细化为可执行测试清单，覆盖正向链路、权限隔离、越权访问、敏感字段、审计生成和停用状态。

## 9. 里程碑建议和验收门槛

### M0：研发前规格冻结

验收门槛：

- 权限矩阵、角色编码、状态流、P0 API 契约冻结。
- 数据模型差异完成决策。
- 密钥管理 MVP 方案明确。
- P0 审计事件清单完成。

### M1：基础身份与租户闭环

验收门槛：

- 超级管理员可登录并创建租户。
- 租户管理员可登录并维护用户、部门。
- 用户停用、租户停用、登录失败、越权访问均有审计记录。

### M2：项目、应用、环境闭环

验收门槛：

- 租户管理员可创建项目并授权项目成员。
- 项目负责人可创建应用、项目公共环境和应用专属环境。
- 敏感环境变量不明文回显，不进入审计明文。

### M3：权限与审计硬化

验收门槛：

- 所有 P0 管理接口完成后端权限校验。
- 跨租户、跨项目、越权授权均被拒绝并记录审计。
- 审计列表和详情可按授权范围查询。

### M4：后续 WP 接入就绪

验收门槛：

- WP2/WP3 可通过接口获取租户、项目、应用、环境上下文。
- 可读取有效配置和策略字段。
- 后续服务可通过内部 API 写入审计事件。
- 完成基础 API 契约测试和权限隔离测试。

## 10. 总体建议

WP1 文档的方向正确，范围与总体方案匹配度高，已经能支撑项目进入“有条件研发拆解”。从项目管理角度，当前最大问题不是缺少大方向，而是若干关键规格尚未冻结，容易在研发过程中引发权限、表结构、接口和安全实现返工。

建议按以下策略推进：

1. 允许进入研发准备和技术预研，但正式 Sprint 开发前必须完成 M0 规格冻结。
2. 优先实现 IAM、租户、RBAC、审计、项目/应用/环境的最小闭环，再扩展 P1/P2 能力。
3. 把权限矩阵、审计事件、接口契约和密钥方案作为 WP1 的四个项目门禁。
4. 严格控制 WP1 边界，只提供模型策略、执行资源、账号池和连接器所需的配置入口，不提前实现后续工作包业务逻辑。
5. 将“租户隔离、权限拒绝、敏感值保护、审计可追踪”作为 WP1 最核心验收标准，而不是只验收页面 CRUD。

综上，WP1 可进入研发任务拆解，但必须以 P0 补充事项完成为前置条件。
