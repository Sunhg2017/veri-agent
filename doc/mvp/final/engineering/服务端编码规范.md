# 服务端编码规范

本文档适用于 `veri-agent` 服务端所有 Java/Spring Boot 模块，包括但不限于 `platform-api` 和 `model-access`。目标是保证模块边界清晰、模块内高内聚低耦合、代码可扩展、可测试、可观测，并且在业务增长后仍能稳定演进。

## 1. 总体原则

1. 服务端代码以业务能力分模块，以模块内分层组织代码。
2. 禁止为了复用少量代码打破业务边界；优先复制少量简单代码，也不要引入跨模块隐式依赖。
3. API 契约、错误码、审计、鉴权、数据库迁移和测试是交付物的一部分，不能视为附属工作。
4. 默认按单平台口径设计，不引入 `tenant_id`、租户表、租户权限或多租户配置。
5. 面向扩展点编程，面向稳定契约集成；扩展点应有清晰接口，契约应有测试保护。
6. 任何涉及密钥、Prompt 明文、用户敏感信息的代码都必须默认脱敏、最小化持久化、禁止写入日志。

## 2. 模块边界

### 2.1 Maven 模块边界

当前后端模块边界如下：

- `platform-api`：WP1 平台控制面，负责认证、账号、RBAC、组织/项目/应用/环境、配置、审计、内部平台上下文。
- `model-access`：WP2 模型接入层，负责供应商配置、Prompt 版本、模型调用、敏感策略、预算、调用审计、WP1 context/audit 集成。
- `db/migration`：数据库结构演进脚本，按 WP 拆分目录。
- `db/validation`：数据库结构、安全约束、种子数据校验脚本。

模块之间只能通过以下方式协作：

- HTTP API。
- 数据库迁移和校验脚本约定。
- 文档化的服务令牌和请求头。

模块之间禁止：

- 一个服务直接读写另一个服务的业务表。
- 复制另一个服务的 repository、service、domain 对象作为内部依赖。
- 通过共享数据库表绕过 API 契约。
- 在 WP2 中重新实现 WP1 的用户、权限、项目生命周期逻辑。

### 2.2 包边界

每个业务模块按能力包组织，例如：

```text
com.songhg.veri.agent.auth
com.songhg.veri.agent.management
com.songhg.veri.agent.integration
com.songhg.veri.agent.modelaccess
```

能力包内按层划分：

```text
api
application
domain
infrastructure
config
security
common
openapi
```

依赖方向必须保持单向：

```text
api -> application -> domain
infrastructure -> application/domain
config/security -> application/common
```

禁止反向依赖：

- `domain` 不依赖 `api`、`infrastructure`、Spring MVC、JdbcTemplate。
- `application` 不依赖 Controller、HTTP request/response、Servlet。
- `api` 不直接访问数据库。
- `infrastructure` 不承载业务编排。

## 3. 分层职责

### 3.1 API 层

API 层包括 Controller、request/response DTO、OpenAPI 注解和接口级校验。

职责：

- 解析 HTTP 请求。
- 绑定、校验和规范化输入边界。
- 返回稳定响应契约。
- 只做薄编排，不承载业务规则。

要求：

- Controller 方法应短小，主要调用 application service。
- DTO 使用 Java `record` 优先，字段通过 `@JsonProperty` 固定外部命名。
- 请求字段必须使用 snake_case，Java 字段使用 camelCase。
- 对外响应字段一旦发布，变更必须通过契约测试保护。
- CSV、文件下载等非 JSON 响应必须显式声明 content type，并有测试覆盖。

禁止：

- Controller 中拼 SQL。
- Controller 中写权限、预算、敏感策略等核心业务判断。
- Controller 返回 Map 作为长期 API 契约，除非是明确的开放扩展字段。

### 3.2 Application 层

Application 层负责业务用例编排，是模块内最核心的行为层。

职责：

- 执行业务流程。
- 调用 domain 规则、repository、外部 client。
- 处理事务边界。
- 生成审计、指标、错误语义。

要求：

- 一个 public 方法对应一个清晰用例，例如 `invoke`、`createProvider`、`activatePrompt`。
- 复杂流程拆成私有方法，但私有方法必须按业务语义命名。
- 对外部依赖使用接口，例如 `ModelAccessRepository`、`PlatformContextClient`、`ModelProviderClient`。
- 业务异常使用统一 `BusinessException + ErrorCode`。
- 对失败路径也要写审计和指标，尤其是 BLOCKED、FAILED、policy violation。

禁止：

- 把 Spring MVC、Servlet、HTTP header 传入 application 方法。
- 直接使用环境变量或系统属性，必须通过 properties/config 注入。
- 把第三方 SDK 对象泄漏到 application 接口。

### 3.3 Domain 层

Domain 层承载业务概念和值对象。

职责：

- 定义领域对象、枚举、值对象。
- 保持业务语义清晰。
- 封装稳定且纯粹的领域判断。

要求：

- 优先使用不可变对象，Java `record` 可优先用于简单领域数据。
- 枚举值必须与数据库约束、API 契约保持一致。
- 领域对象不能依赖 Spring、JdbcTemplate、RestClient。

禁止：

- 在 domain 中执行数据库访问、HTTP 调用、读取环境变量。
- 为了接口返回便利在 domain 中加入展示字段或分页字段。

### 3.4 Infrastructure 层

Infrastructure 层负责技术实现细节。

职责：

- Repository 实现。
- 外部 HTTP client。
- 第三方 provider adapter。
- 持久化映射。

要求：

- Infrastructure 实现 application 定义的接口。
- DB profile 与 local profile 的行为必须尽量一致。
- SQL 字段顺序、record 构造参数、migration 字段必须同步维护。
- 外部调用必须设置超时。
- 外部错误必须转换成业务可理解的错误消息，不能透传密钥、请求体、完整第三方响应。

禁止：

- Infrastructure 主导业务流程。
- 在 repository 中做复杂业务策略判断。
- 在外部 client 中写入审计日志。

## 4. API 契约规范

### 4.1 JSON Envelope

普通 JSON API 统一返回：

```json
{
  "code": "OK",
  "message": "success",
  "trace_id": "trc_xxx",
  "data": {}
}
```

例外：

- CSV 导出。
- 文件下载。
- Actuator endpoint。

例外必须在测试中明确断言。

### 4.2 命名规范

HTTP JSON 字段使用 snake_case：

```json
{
  "project_id": "project-001",
  "sensitivity_level": "INTERNAL"
}
```

Java 字段使用 camelCase：

```java
@JsonProperty("project_id") String projectId
```

数据库字段使用 snake_case，与迁移脚本一致。

### 4.3 分页规范

分页接口统一使用：

- `page`：从 0 开始。
- `size`：服务端必须设置上限。
- 响应包含 `items`、`page`、`size`、`total`。

分页参数必须在 service 层做安全归一化，禁止无限制查询。

### 4.4 错误码规范

错误码必须稳定、可监控、可文档化。

要求：

- 业务失败使用 `BusinessException(ErrorCode, message)`。
- message 面向调用方可读，不包含密钥、token、Prompt 明文、完整 SQL、完整第三方响应。
- 新增错误码必须评估 HTTP status 是否准确。
- 测试必须断言关键错误码。

常见错误语义：

- `BAD_REQUEST`：输入格式或业务参数非法。
- `FORBIDDEN`：鉴权、服务令牌或权限失败。
- `NOT_FOUND`：资源不存在。
- `CONFLICT` / `INVALID_STATE`：状态冲突。
- `MODEL_POLICY_VIOLATION`：模型策略阻断。
- `BUDGET_EXCEEDED`：预算阻断。
- `MODEL_PROVIDER_UNAVAILABLE`：供应商不可用或外部调用失败。
- `SENSITIVE_CONTENT_BLOCKED`：敏感内容阻断。

## 5. 鉴权与上下文

### 5.1 用户 API

用户态 API 使用 Bearer access token，由 WP1 鉴权模块解析用户身份。

要求：

- 需要权限控制的接口必须在 application 或 controller 边界调用授权服务。
- 权限码必须来自权限矩阵。
- 拒绝访问必须写审计。

### 5.2 模块内集成 API

MVP 阶段 WP1、WP2、WP3 属于同一个 `platform-api` Java 服务内的领域模块。模块之间优先通过 Spring 应用服务调用；保留的内部 HTTP API 仅作为外部集成契约，不作为同服务内模块互调方式。外部或未来服务化调用使用服务令牌和调用方上下文头：

```text
Authorization: Bearer <SERVICE_TOKEN>
X-Caller-Service: <service-name>
X-Delegated-User-Id: <user-id>
X-Trace-Id: <trace-id>
```

要求：

- WP2 调 WP1 只能通过 `/api/v1/contexts/**` 和 `/api/v1/audit/events` 等内部契约。
- 服务令牌必须通过环境变量配置，禁止写入代码、文档示例之外的配置文件。
- 策略敏感调用必须校验调用服务和委托用户。

## 6. 数据库与迁移规范

### 6.1 Migration

要求：

- 按 WP 目录拆分：`db/migration/wp1`、`db/migration/wp2`。
- 文件名使用 Flyway 风格：`VyyyyMMdd_NNN__description.sql`。
- migration 必须可重复执行关键安全片段，必要时使用 `if not exists` 或 `do $$`。
- migration 不得修改其他 WP 的表，除非有明确跨 WP 交付说明。
- 删除字段必须配套代码、测试、validation 和文档同步。

### 6.2 Validation

每个 schema 关键约束都必须进入 validation：

- 核心表存在。
- 关键字段存在。
- 关键索引存在。
- 敏感明文字段不存在。
- 种子数据存在。
- 单平台约束不回退，例如不得重新引入 `tenant_id`。

DB validation 失败视为不可交付。

### 6.3 SQL 编码

要求：

- 使用参数绑定，禁止字符串拼接用户输入。
- 列名必须显式列出，禁止生产代码使用 `select *`。
- 查询必须带分页或明确上限。
- 复杂查询优先封装在 repository 私有方法中。
- `created_at`、`updated_at` 由服务端统一生成或数据库默认生成，不能混乱。

## 7. 配置规范

所有运行时配置通过 `@ConfigurationProperties` 绑定。

要求：

- 配置项命名必须有模块前缀，例如 `veri-agent.model-access.*`。
- 环境变量使用 WP 前缀，例如 `WP2_SERVICE_TOKEN`。
- 配置默认值只允许用于本地开发；生产敏感配置必须显式传入。
- 新增配置必须写 README，说明默认值、用途、安全影响。

禁止：

- 在业务代码中散落 `System.getenv()`，除 provider 密钥引用解析这类明确边界外。
- 在日志中打印完整配置对象。
- 将 token、api key、密码写入示例配置文件。

## 8. 安全与敏感数据

### 8.1 密钥

要求：

- 外部 provider 密钥只能保存引用，例如 `env:MODEL_API_KEY`。
- 数据库禁止存储明文密钥。
- API 响应只返回 `api_key_ref`，不得返回密钥值。

### 8.2 Prompt 与模型调用

要求：

- 调用日志只保存 digest 和脱敏 preview。
- CSV 导出不得包含 Prompt 明文、原始请求体、密钥、第三方完整响应。
- 敏感内容阻断要早于 provider 调用。
- 高敏感级别必须在 provider 选择前执行策略校验。

### 8.3 日志

日志允许：

- trace_id。
- invocation_id。
- provider_name。
- 错误码。
- 脱敏后的短错误描述。

日志禁止：

- access token。
- service token。
- api key。
- password。
- Prompt 明文。
- 完整模型响应。

## 9. 可观测性规范

### 9.1 Trace

要求：

- 所有请求必须有 `trace_id`。
- 响应头返回 `X-Trace-Id`。
- 日志 pattern 必须包含 trace_id。
- 模块内调用复用当前 trace，上下游 HTTP 边界透传 `X-Trace-Id`。

### 9.2 Metrics

关键业务路径必须有指标：

- 成功、失败、阻断次数。
- 外部 provider latency。
- fallback 次数。
- budget blocked 次数。
- audit 写入成功/失败/跳过。
- token 和 cost 汇总。

指标标签要求：

- 使用低基数字段，例如 `status`、`provider_type`、`sensitivity_level`、`error_code`。
- 禁止使用 user_id、project_id、invocation_id、prompt_key 作为指标标签。

### 9.3 Audit

要求：

- 权限拒绝、账号生命周期、模型调用、策略阻断必须可审计。
- 审计内容不保存敏感明文。
- 审计写入失败的策略必须明确。
- WP2 写 WP1 audit 失败不阻断主调用，但必须记录 WARN 和 metrics。

## 10. 扩展点规范

### 10.1 Provider Adapter

新增模型供应商必须实现 `ModelProviderClient`。

要求：

- `supports` 只判断 provider 类型。
- `call` 内部处理第三方协议细节。
- 设置连接和读取超时。
- 将第三方错误转换为统一业务异常。
- 不泄漏第三方 SDK 对象到 application 层。
- 不在 adapter 内写 DB、审计、业务策略。

### 10.2 Repository

新增持久化能力必须先定义 application repository 接口，再实现 local/db 两套行为。

要求：

- local profile 便于测试和前端联调。
- db profile 面向生产持久化。
- 两套实现的排序、过滤、分页语义必须一致。

### 10.3 Policy

策略逻辑必须集中：

- 敏感级别归一化集中处理。
- public model routing 策略集中处理。
- budget guardrail 集中处理。
- 不允许在多个 Controller 或 Repository 中散落同一策略。

## 11. 测试规范

### 11.1 测试层次

每个服务端改动按风险选择测试：

- 纯函数：单元测试。
- application service：业务路径测试。
- Controller：MockMvc API 契约测试。
- OpenAPI：契约快照/关键字段测试。
- DB：migration + validation。
- 系统集成：同一 `platform-api` 内模块策略 smoke，外部 HTTP 边界 smoke。

### 11.2 必测场景

新增 API 必须覆盖：

- 成功路径。
- 鉴权失败。
- 参数校验失败。
- 关键业务错误码。
- 响应字段契约。

新增持久化能力必须覆盖：

- migration 首次执行。
- migration 重复执行。
- validation。
- seed 数据。
- local/db 行为一致性。

新增模型调用能力必须覆盖：

- 敏感内容阻断。
- 策略阻断。
- provider 成功。
- provider 失败。
- fallback。
- 审计和指标。

### 11.3 质量门禁

提交前至少运行：

```bash
mvn test
```

涉及 WP1 DB：

```bash
bash db/validation/run_wp1_db_validation.sh
```

涉及 WP2 DB：

```bash
bash db/validation/run_wp2_db_validation.sh
```

涉及 WP2 HTTP API：

```bash
WP2_SERVICE_TOKEN=local-model-access-token bash scripts/wp2_model_access_smoke.sh
```

涉及 WP1/WP2 模块策略集成：

```bash
WP1_SERVICE_TOKEN=local-platform-service-token \
WP1_AUTH_TOKEN_SECRET=local-auth-secret \
WP2_SERVICE_TOKEN=local-model-access-token \
bash scripts/wp2_module_policy_smoke.sh
```

## 12. 代码风格

### 12.1 Java

要求：

- 使用 Java 21。
- 优先使用构造器注入。
- 简单 DTO 使用 `record`。
- 公共方法名使用业务动词。
- 私有方法保持短小，避免超过一个明显业务步骤。
- 集合返回空集合，不返回 null。
- 时间使用 `Instant` 存储事件时间，日窗口使用明确 `ZoneId`。
- 金额和成本使用 `BigDecimal`。

禁止：

- 字符串魔法值散落在多处；应使用 enum、常量或集中方法。
- 捕获异常后静默吞掉。
- 在生产代码中使用 `printStackTrace`。
- 大段复制粘贴业务逻辑。
- 将测试辅助代码放入 main source。

### 12.2 注释

注释只解释为什么，不复述代码在做什么。

适合写注释：

- 安全策略。
- 兼容历史数据的原因。
- 复杂 SQL 的业务意图。
- 非显然的降级策略。

不适合写注释：

- getter/setter。
- 直白赋值。
- 与代码明显重复的流程描述。

## 13. 评审检查清单

代码评审必须检查：

- 模块边界是否被破坏。
- 依赖方向是否正确。
- Controller 是否过重。
- 业务规则是否集中。
- 是否有稳定错误码。
- 是否有脱敏、审计、指标。
- 是否引入敏感明文字段。
- 是否重新引入 `tenant_id` 或多租户口径。
- 是否更新 migration 和 validation。
- 是否更新 README/交付文档。
- 是否覆盖关键测试。
- 是否有无限查询、无超时外部调用、无上限导出。

## 14. 允许例外

允许例外必须满足：

1. 在 PR 或交付说明中写明原因。
2. 给出回收计划或长期维护理由。
3. 不绕过安全、审计、密钥、单平台约束。
4. 有测试证明例外路径稳定。

未经说明的例外视为技术债，不应进入主干。
