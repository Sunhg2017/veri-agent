## 1. 测试视角总体结论

**结论：有条件通过。**

WP1 PRD 和系统架构设计已覆盖平台基础底座的主要测试对象，包括租户、部门、用户、项目、应用、环境、角色权限、审计日志，以及多租户隔离、RBAC、敏感配置保护、审计追踪等质量关键点。从 QA 角度看，当前文档已经可以支撑测试分析、测试范围划分和 P0 主链路测试设计。

但当前仍不建议直接进入完整测试用例设计和自动化脚本开发。原因是若干测试输入尚未冻结，尤其是权限矩阵、P0 API 契约、状态流、初始化/登录策略、密钥管理方案、审计事件编码和数据模型一对多规则。上述内容如果不补齐，接口自动化、权限越权测试、审计覆盖率验证和 UI 验收都会出现口径不一致，导致测试用例大量返工。

进入研发与测试并行准备的前置条件：

1. 冻结 MVP 角色、权限点、菜单权限、数据范围和授权作用域矩阵。
2. 输出 P0 API 契约，包含请求/响应、错误码、分页筛选、排序、幂等、状态流、审计事件编码和权限点。
3. 明确超级管理员初始化、租户管理员创建、邀请激活、登录、登出、会话过期、用户停用后的会话失效规则。
4. 明确敏感配置的 MVP 落地方案，包含普通变量、敏感变量、密钥引用、脱敏展示、审计脱敏和导出脱敏。
5. 输出 P0 审计事件清单，并明确成功、失败、拒绝三类事件是否记录。

## 2. 可测性评估

### 2.1 PRD 可测性

PRD 的模块边界清晰，按租户、部门、用户、项目、应用、环境、角色权限、审计日志拆分功能，并给出 P0/P1/P2 优先级、关键流程、数据隔离规则、唯一性规则、状态规则、权限校验规则、敏感数据规则和验收标准。整体具备测试设计基础。

可测性较好的部分：

- 核心业务对象字段明确，可拆分字段校验、唯一性、状态流、权限数据范围和列表查询测试。
- P0 功能范围基本完整，可形成基础配置闭环验收链路。
- 多租户隔离、后端权限校验、敏感值不明文、审计 100% 覆盖等关键质量目标明确。
- Web 管理后台页面建议覆盖列表、表单、二次确认、详情、筛选、分页、空状态和错误态。

可测性不足的部分：

- 验收标准仍偏描述性，缺少可直接执行的 Given/When/Then 或用例级判定条件。
- 权限矩阵未冻结，角色与架构命名不一致，无法稳定设计角色 x 资源 x 动作 x 作用域测试。
- 登录、会话、邀请激活、密码策略、锁定策略和停用失效规则不完整。
- 状态流缺少允许迁移和禁止迁移清单，例如项目筹备中、进行中、归档、停用之间是否可逆。
- 字段级规格不足，部分页面缺少必填、长度、格式、枚举、默认值、是否可编辑、唯一性冲突提示。
- P0/P1/P2 中导出、失败审计、健康检查、环境复制等边界需进一步冻结，否则测试范围容易膨胀。

### 2.2 架构设计可测性

架构设计提供了模块划分、核心领域模型、隔离策略、RBAC 流程、审计事件结构、环境配置模型、关键 API 草案和数据库表草案，能够支撑接口测试、集成测试、安全测试和自动化测试框架设计。

可测性较好的部分：

- `SecurityContext`、`tenant_id`、`project_id`、`scope_type/scope_id`、权限缓存和审计 outbox 等设计为测试注入与断言提供了明确观察点。
- API 草案已覆盖租户、部门、用户、角色、项目、应用、环境、配置、审计等主资源。
- 审计事件结构字段较完整，可设计审计字段完整性、脱敏、查询隔离和 Trace ID 关联测试。
- 配置继承优先级明确，可设计 Environment > Application > Project > Tenant > System Default 的覆盖测试。

可测性不足的部分：

- API 仍是草案级，缺少 DTO、错误码、分页格式、筛选参数、排序规则、幂等策略和批量更新语义。
- 项目公共环境接口缺失或不清晰，当前 API 主要通过 `/applications/{appId}/environments` 创建应用环境。
- `base_project.dept_id` 与 PRD 的项目多部门关联不一致，影响数据准备和权限继承测试。
- 部门负责人、项目负责人、应用负责人是否支持多人，架构与 PRD 表达不一致。
- `plain_value` 与“密钥不落明文”原则存在解释风险，需要明确普通变量可明文、敏感变量不可明文。
- 审计写入失败进入补偿队列的最终一致性验收标准不明确。

## 4. 功能测试重点

### 4.1 租户

- 创建租户成功后生成租户记录、预置角色、基础权限和租户管理员绑定。
- 租户名称、编码唯一性校验，编码全局唯一，大小写与特殊字符规则需明确。
- 编辑租户只允许修改非关键字段，租户编码是否可修改需冻结。
- 停用租户后，租户内普通用户不可登录，不可访问 API，不可通过旧 Token 继续操作。
- 平台超级管理员仍可查看和恢复停用租户，普通租户管理员不可跨租户查看。
- 租户创建、编辑、启停、管理员绑定均生成审计。

### 4.2 部门

- 部门树按租户隔离展示，跨租户部门不可见、不可引用。
- 同一父部门下部门名称和编码唯一，跨父级或跨租户是否允许重复需按规则验证。
- 创建、编辑、启停部门时校验父部门状态、层级循环、非法移动。
- 停用部门后不可作为新用户主部门；已有用户、子部门和项目关联的处理规则需补充后测试。
- 部门负责人单人还是多人需冻结，测试需覆盖负责人增删与权限影响。

### 4.3 用户

- 创建/邀请用户时校验登录账号租户内唯一、邮箱/手机号格式、主部门必填。
- 用户可属于多个部门且必须有主部门；主部门停用、移除主部门时需有阻断或替换规则。
- 启用、停用、锁定用户后登录和会话行为符合状态规则。
- 用户角色分配后，`/auth/me`、菜单权限、项目列表和可访问资源实时变化。
- 用户权限详情准确展示租户级、项目级、应用级角色，且只能展示操作者有权查看的数据。

### 4.4 项目

- 租户管理员或有 `project:create` 权限的用户可创建项目。
- 项目名称、编码在租户内唯一；编码格式、长度和修改规则需冻结。
- 项目负责人可添加成员、移除成员、分配项目级角色，但不能越权授予租户管理员。
- 项目状态流覆盖筹备中、进行中、归档、停用；不同状态下新增应用、环境、成员的限制需验证。
- 项目关联多部门或主部门的最终模型需冻结后覆盖权限继承和筛选查询。

### 4.5 应用

- 应用必须归属于项目，应用编码项目内唯一，跨项目是否可重复需验证。
- 应用类型使用枚举，非法类型不可保存。
- 应用负责人支持单人或多人需冻结，并验证负责人权限来源。
- 停用应用后不可新增环境，不可作为后续测试资产或执行目标，历史数据仍可只读查看。
- 应用敏感级别、是否允许公有云模型等字段在 WP1 只验证保存、读取、审计，不验证模型路由。

### 4.6 环境

- 支持项目公共环境和应用专属环境，两类环境的创建、查询、编辑接口与页面入口必须清晰。
- 环境名称唯一规则按“项目公共环境内唯一、同一应用下唯一”验证。
- 基础地址校验 URL 格式，API Base URL、Web URL 可为空或必填需按环境类型明确。
- 普通变量可查看明文，敏感变量保存后只展示掩码，不在响应、日志、审计、导出中出现明文。
- 环境启停后，停用环境不可被后续执行模块选择；WP1 阶段至少验证状态字段和查询约束。
- 生产只读环境默认关闭自动化执行开关，修改高风险配置需二次确认和审计。

### 4.7 角色权限

- 新租户初始化预置角色和权限点，角色编码、名称、层级与 PRD/架构保持一致。
- 内置角色不可删除，是否允许编辑需按冻结规则验证。
- 角色绑定必须包含主体、角色、作用域、租户上下文和状态。
- 授权人不能授予超过自身范围的角色，不能跨租户授权，不能给项目成员授予租户级管理员。
- 权限变更后立即生效，权限缓存失效，旧 Token 不应保留已撤销权限。

### 4.8 审计日志

- 成功、失败、拒绝三类事件均有明确记录策略。
- P0 创建、编辑、启停、授权、导出、登录、登出、登录失败、越权访问生成审计日志。
- 审计详情包含操作人、时间、租户、动作、资源、结果、请求 IP、User-Agent、Trace ID、变更摘要。
- 审计日志按租户、项目、应用、环境授权范围隔离。
- 审计日志只追加，不允许普通业务用户修改或删除。

## 5. 权限与安全测试重点

### 5.1 多租户隔离

- 用户 A 属于租户 T1，不得通过列表、详情、编辑、删除、授权、审计查询访问 T2 数据。
- API 不允许客户端传入任意 `tenant_id` 覆盖 Token 中的租户上下文。
- 跨租户资源 ID 枚举应返回 403 或 404，错误响应不得泄露资源存在性细节，具体口径需统一。
- 唯一性校验需按租户边界生效，除租户编码和权限编码外不应跨租户误判冲突。
- 审计日志、配置读取、项目列表、用户列表均需验证租户隔离。

### 5.2 RBAC 与越权

- 覆盖角色 x 资源 x 动作 x 作用域矩阵，至少包含 SuperAdmin/TenantAdmin/ProjectOwner/AppOwner/Tester/Developer/Auditor 或最终冻结角色。
- 验证前端隐藏入口后，直接调用 API 仍被后端拒绝。
- 验证越权查看、越权编辑、越权授权、越权导出、越权启停、越权读取敏感配置。
- 验证部门角色、项目角色、应用角色、环境角色的作用域边界。
- 验证权限移除、角色停用、用户停用后权限立即失效。

### 5.3 停用状态

- 停用租户：租户内普通用户不可登录，旧会话不可继续访问。
- 停用用户或锁定用户：登录失败，现有会话失效。
- 停用部门：不可作为新用户主部门，是否影响已有用户需有规则。
- 归档/停用项目：不可新增应用、环境、成员，历史数据只读。
- 停用应用：不可新增环境，不可被后续资产引用。
- 停用环境：不可被后续执行选择，WP1 验证状态与读取约束。

### 5.4 敏感信息脱敏

- 敏感值不得出现在数据库明文字段、接口响应、前端页面、日志、审计 diff、导出文件中。
- 敏感字段更新时只记录“是否变更”、密钥引用 ID 或脱敏摘要。
- 普通变量和敏感变量的创建、编辑、覆盖、删除需要分别测试。
- 低权限用户查看环境详情时只能看到脱敏值或无敏感字段。
- 导出用户、环境、审计数据时按权限过滤敏感字段。

## 6. 接口测试建议

### 6.1 关键 API 覆盖

P0 接口自动化建议优先覆盖：

- 认证与当前用户：登录、登出、刷新或会话续期、`GET /auth/me`。
- 租户：`POST /admin/tenants`、`GET /tenants/current`、`PATCH /tenants/current`、租户启停接口。
- 部门：`GET /departments/tree`、`POST /departments`、`PATCH /departments/{deptId}`、成员增删接口。
- 用户：`GET /users`、`POST /users`、`PATCH /users/{userId}`、`PATCH /users/{userId}/status`。
- 角色与授权：`GET /roles`、`POST /role-bindings`、`DELETE /role-bindings/{bindingId}`、角色权限查看接口。
- 项目：`GET /projects`、`POST /projects`、`GET /projects/{projectId}`、`PATCH /projects/{projectId}`、项目成员增删接口。
- 应用：`GET /projects/{projectId}/applications`、`POST /projects/{projectId}/applications`、`PATCH /applications/{appId}`。
- 环境：项目公共环境接口、`GET /applications/{appId}/environments`、`POST /applications/{appId}/environments`、`GET /environments/{envId}`、`PATCH /environments/{envId}`、`PUT /environments/{envId}/variables`。
- 配置与审计：`GET /configs/effective`、`PUT /configs`、`POST /audit/events`、`GET /audit/events`、`GET /audit/events/{eventId}`。

### 6.2 鉴权与上下文

- 所有管理接口均需带 Token 验证，未登录返回 401。
- 无权限访问返回 403，并写入拒绝审计。
- 资源不存在、资源存在但无权限的返回口径需统一。
- 认证上下文中的 `tenant_id/user_id/session_id` 应由服务端解析，不接受客户端伪造。
- 服务间内部审计写入 API 需要独立服务身份鉴权，不能被普通用户 Token 调用。

### 6.3 错误码

建议冻结统一错误码类型并纳入接口自动化断言：

- 参数非法：必填缺失、格式错误、长度超限、枚举非法。
- 唯一性冲突：编码、名称、账号重复。
- 状态非法：停用资源不可编辑、归档项目不可新增。
- 权限不足：无菜单权限、无资源权限、越权授权。
- 资源不存在：ID 不存在或已删除。
- 敏感配置非法：敏感值明文读取、密钥引用格式错误。
- 系统异常：审计写入补偿、外部密钥服务不可用。

### 6.4 幂等、分页筛选和状态流

- 创建类接口建议支持幂等键或明确不支持幂等；至少测试重复提交是否产生重复数据。
- 启停、状态变更、角色绑定删除等接口需验证重复调用结果。
- 列表接口统一验证分页参数、默认排序、非法分页、筛选组合、空结果、跨租户过滤。
- 状态变更接口需验证允许流转和禁止流转，例如项目归档后是否可恢复、停用后是否可启用。
- 批量更新环境变量需明确覆盖语义、增量语义、删除语义和部分失败处理。

## 7. UI 测试建议

### 7.1 Web 管理后台页面

P0 UI 测试应覆盖：

- 登录页、会话过期跳转、无权限页。
- 租户管理页、组织部门页、用户管理页。
- 项目列表、项目详情、成员管理。
- 应用列表、应用详情。
- 环境列表、环境配置页。
- 角色管理、授权管理。
- 审计日志列表和审计详情。

### 7.2 表单测试

- 必填、长度、格式、唯一性、枚举、默认值、禁用态、只读态。
- 创建、编辑、取消、保存失败、保存成功、重复提交。
- 字段级错误和全局错误同时存在时的展示。
- 敏感字段创建后不回显明文，再次编辑时只允许覆盖或清空。
- 编码类字段建议限制字母、数字、下划线和中划线，并验证前后端一致。

### 7.3 列表与查询

- 默认筛选、分页、排序、关键词搜索、状态筛选、部门/项目/应用筛选。
- 筛选条件和分页状态保留。
- 空状态、加载态、接口错误态、无权限状态。
- 列表操作按钮按权限展示，但后端仍需拒绝越权调用。

### 7.4 二次确认与高风险操作

- 租户停用、用户停用/锁定、项目归档/停用、应用停用、环境停用。
- 角色授权、角色解绑、环境敏感变量变更、审计导出。
- 二次确认需展示影响范围，取消后不产生业务变更和审计成功事件。
- 确认后若接口失败，应展示明确错误，不应误显示成功。

### 7.5 空状态和错误态

- 新租户无部门、无用户、无项目、无应用、无环境、无审计日志时应有可理解空状态。
- 无权限访问页面不暴露资源名称、敏感字段或其他租户信息。
- 网络错误、服务端错误、参数校验错误需有区分展示。
- 会话失效时跳转登录，重新登录后是否返回原页面需按产品规则验证。

## 8. 审计测试建议

### 8.1 审计事件覆盖

建议在 P0 阶段输出审计事件清单，并按清单逐项验证：

- 登录成功、登录失败、登出、账号锁定、Token 刷新。
- 创建、编辑、启停租户，指定租户管理员。
- 创建、编辑、启停部门，成员加入/移除。
- 创建、编辑、启停用户，分配/移除角色。
- 创建角色、编辑角色、绑定角色、解绑角色、修改权限。
- 创建、编辑、归档、停用项目，项目成员变更。
- 创建、编辑、停用应用，应用负责人变更。
- 创建、编辑、停用环境，URL 变更、变量变更、鉴权配置变更。
- 审计导出、用户导出、配置导出。
- 无权限访问、越权访问尝试、敏感配置修改失败。

### 8.2 失败审计

- 登录失败需记录失败原因分类，但不泄露账号是否存在的敏感信息。
- 参数校验失败是否审计需分级，安全相关失败建议记录。
- 权限拒绝由鉴权过滤器写入审计，需验证业务方法未执行。
- 审计写入失败不阻断主流程，但需进入补偿队列并可监控。

### 8.3 审计查询和导出

- 按时间、操作人、资源类型、动作、结果、项目、应用筛选。
- 默认查询最近 7 天或固定时间范围，超大范围限制需明确。
- 审计详情字段完整，Trace ID 可关联请求日志。
- 审计导出按权限和筛选条件生效，导出文件不包含敏感明文。
- 导出行为本身必须记录审计日志。

## 9. 自动化测试建议

### 9.1 适合接口自动化

接口自动化应作为 WP1 回归主力，建议覆盖：

- 租户初始化到项目、应用、环境配置的 P0 正向闭环。
- 多租户隔离和跨租户资源 ID 枚举。
- RBAC 权限矩阵、越权访问、越权授权。
- 用户、租户、项目、应用、环境停用后的接口限制。
- 敏感变量保存、读取、更新、审计脱敏。
- 审计事件生成、查询、详情字段完整性。
- 分页、筛选、唯一性、错误码、状态流。
- 配置继承和有效配置读取。

建议优先使用契约驱动的接口测试：OpenAPI 契约冻结后生成基础请求模型，再补充业务断言和权限矩阵数据驱动用例。

### 9.2 适合 UI 自动化

UI 自动化建议只覆盖稳定、高价值、低变动的路径：

- 登录、切换上下文、菜单可见性。
- 租户初始化主链路。
- 创建部门、创建用户、创建项目、添加项目成员、创建应用、创建环境。
- 敏感环境变量页面不回显明文。
- 审计日志按资源查询并查看详情。
- 高风险操作二次确认。

不建议在早期对所有字段校验做 UI 自动化，字段校验应主要放在接口层；UI 只保留少量代表性用例验证交互和前后端串联。

### 9.3 先人工验证

以下内容建议先人工验证，待交互和规格稳定后再自动化：

- 部门树拖拽或层级移动。
- 自定义角色权限树配置。
- 环境变量复杂编辑、批量覆盖、变更摘要确认。
- 审计导出文件格式和大数据量导出。
- 会话过期、并发登录、权限变更后页面实时刷新体验。
- 审计 outbox 补偿、密钥服务异常等故障注入场景。

## 10. 测试数据与账号准备建议

### 10.1 基础租户数据

至少准备三个租户：

- `tenant_a`：主测试租户，包含完整部门、用户、项目、应用、环境。
- `tenant_b`：隔离验证租户，用于跨租户越权和数据不可见测试。
- `tenant_disabled`：停用租户，用于停用状态验证。

### 10.2 组织与账号

每个主测试租户建议准备：

- 平台超级管理员：用于租户创建和全局审计。
- 租户管理员：用于组织、用户、角色、项目管理。
- 部门负责人：用于部门范围查看和后续权限验证。
- 项目负责人或项目管理员：用于项目成员、应用、环境管理。
- 应用负责人：用于应用和环境配置验证。
- 测试工程师：用于授权项目查看和环境使用验证。
- 研发工程师：用于只读查看验证。
- 只读审计员：用于审计只读权限验证。
- 无项目成员用户：用于未授权访问验证。
- 停用用户、锁定用户：用于登录和会话失效验证。

### 10.3 项目、应用和环境

建议准备：

- 项目 `project_alpha`：进行中，包含完整成员、应用和环境。
- 项目 `project_beta`：同租户不同项目，用于跨项目隔离。
- 项目 `project_archived`：归档项目，用于只读验证。
- 项目 `project_disabled`：停用项目，用于禁止新增验证。
- 应用 `admin_web`：Web 管理后台类型。
- 应用 `http_api`：HTTP API 类型。
- 环境 `DEV`、`TEST`、`STAGING`、`PROD`、`CUSTOM`，其中 `PROD` 默认执行开关关闭。
- 普通变量 `BASE_URL`、`API_BASE_URL`、`TENANT_CODE`。
- 敏感变量 `ADMIN_PASSWORD`、`API_TOKEN`、`COOKIE_SECRET`，仅使用密钥引用或加密值。

### 10.4 权限矩阵数据

建议以数据驱动方式维护：

- 角色、资源、动作、作用域、预期结果。
- 操作用户、目标资源所属租户、目标资源所属项目、目标资源状态。
- 成功后预期审计事件编码。
- 失败后预期错误码和审计结果。

## 11. 验收标准缺口和建议补充的测试用例类型

### 11.1 验收标准缺口

| 缺口 | 影响 | 建议补充 |
|---|---|---|
| 权限矩阵未冻结 | 无法稳定设计越权和菜单权限用例 | 输出角色 x 资源 x 动作 x 作用域矩阵 |
| API 契约不完整 | 接口自动化和前后端联调缺少断言基础 | 输出 OpenAPI、错误码、分页筛选、状态流、审计编码 |
| 初始化和登录流程不足 | IAM 主链路验收不可执行 | 补充超级管理员、租户管理员、邀请激活、密码、会话策略 |
| 状态流不完整 | 停用、归档、锁定测试口径不一致 | 输出资源状态流与各状态可操作矩阵 |
| 敏感配置方案未定 | 脱敏、安全和审计测试不可落地 | 明确 SecretProvider、密钥引用、加密、脱敏、迁移策略 |
| 审计事件清单缺失 | 审计覆盖率 100% 难以验收 | 输出 P0 审计事件编码、触发点、结果类型、字段要求 |
| 项目公共环境接口不清 | 环境管理 P0 范围无法完整自动化 | 补充项目公共环境 API 和 UI 入口 |
| 数据模型一对多冲突 | 部门/负责人/项目关联测试会返工 | 冻结项目部门、负责人多人规则和表结构 |

### 11.2 建议补充的测试用例类型

- 正向主链路用例：租户初始化、组织配置、项目配置、应用配置、环境配置、授权、审计查询。
- 权限矩阵用例：每个角色对每类资源的查看、创建、编辑、启停、授权、导出。
- 多租户隔离用例：跨租户列表、详情、编辑、授权、审计、配置读取。
- 状态流用例：用户、租户、项目、应用、环境、角色的状态变化及操作限制。
- 敏感信息用例：保存、读取、更新、审计、导出、日志脱敏。
- 审计用例：成功、失败、拒绝、补偿、查询、详情、导出。
- 接口契约用例：参数校验、错误码、分页筛选、幂等、重复提交、状态非法。
- UI 交互用例：表单、列表、二次确认、空状态、错误态、无权限页。
- 配置继承用例：租户、项目、应用、环境不同层级覆盖和来源返回。
- 并发和一致性用例：重复授权、并发启停、权限缓存失效、审计 outbox 重试。

## 12. 质量风险与阻塞项

| 等级 | 风险/阻塞项 | 测试影响 | 建议处理 |
|---|---|---|---|
| P0 | 权限矩阵未冻结 | 权限测试、越权测试、菜单测试、自动化数据驱动均无法稳定 | 研发前冻结 MVP 权限矩阵 |
| P0 | P0 API 契约未冻结 | 接口自动化无法开发，错误码和断言不一致 | 输出 OpenAPI 与错误码规范 |
| P0 | 初始化和登录策略不完整 | IAM 主链路和停用会话测试不可执行 | 补齐初始化、登录、会话、锁定、停用规则 |
| P0 | 敏感配置落地方案未定 | 环境模块安全验收存在阻塞 | 明确 SecretProvider、密钥引用和脱敏策略 |
| P0 | PRD 与架构一对多模型不一致 | 项目部门、负责人、公共环境用例会返工 | 冻结数据模型差异决策 |
| P1 | 审计事件编码未清单化 | 审计覆盖率无法量化 | 输出 P0 审计事件清单 |
| P1 | 状态流不完整 | 停用、归档、锁定测试口径不统一 | 输出状态流和状态操作矩阵 |
| P1 | 审计 outbox 验收标准不足 | 故障补偿与最终一致性无法验证 | 明确重试、告警、补偿完成标准 |
| P1 | 配置继承缺少删除/恢复默认规则 | 有效配置测试缺少边界 | 明确覆盖、删除、恢复和来源返回 |
| P2 | UI 字段级规格不足 | 页面测试容易依赖实现猜测 | 补充字段校验、文案和错误提示规范 |

## 13. 建议的测试计划与测试里程碑

### M0：测试规格冻结

目标：让 QA 能开始稳定编写测试用例和接口自动化框架。

准入条件：

- 权限矩阵、角色编码、菜单权限、状态流冻结。
- P0 API 契约、错误码、分页筛选、审计事件编码冻结。
- 初始化、登录、会话、用户停用、租户停用规则冻结。
- 敏感配置 MVP 方案冻结。
- P0 测试数据模型和账号模型确认。

测试产出：

- WP1 测试方案。
- P0 测试用例清单。
- 权限矩阵测试数据。
- 接口自动化目录与基础数据工厂设计。

### M1：IAM、租户与组织测试

目标：验证平台基础身份和租户组织闭环。

测试重点：

- 超级管理员登录并创建租户。
- 租户管理员维护部门、用户和租户级角色。
- 登录失败、用户停用、租户停用、会话失效。
- 租户隔离、基础审计、无权限访问。

退出标准：

- IAM、租户、部门、用户 P0 用例通过。
- 登录、停用、越权访问均有审计。
- P0 缺陷清零，P1 高风险缺陷有规避方案。

### M2：项目、应用、环境测试

目标：验证 WP1 支撑后续测试资产和执行上下文的基础能力。

测试重点：

- 创建项目、授权项目成员、项目状态管理。
- 创建应用、维护应用负责人、应用启停。
- 创建项目公共环境和应用专属环境。
- 普通变量、敏感变量、鉴权配置、脱敏展示。
- 环境状态和生产只读策略字段。

退出标准：

- 租户到项目、应用、环境的基础配置闭环通过。
- 敏感值不在页面、接口、审计、日志、导出中明文出现。
- 关键状态约束生效。

### M3：RBAC 与审计硬化测试

目标：验证 WP1 的安全边界和可追踪能力。

测试重点：

- 全量 P0 权限矩阵。
- 跨租户、跨项目、越权授权、越权导出。
- 权限变更后缓存失效和旧会话权限收敛。
- P0 审计事件覆盖率、审计查询隔离、审计详情字段完整。
- 审计 outbox 补偿和失败记录。

退出标准：

- P0 管理接口后端鉴权覆盖率 100%。
- P0 审计事件覆盖率 100%。
- 高危越权和敏感信息泄露缺陷清零。

### M4：自动化回归与后续 WP 接入验证

目标：形成可持续回归基础，验证 WP1 可被后续工作包复用。

测试重点：

- 接口自动化覆盖 P0 主链路、权限矩阵、审计、敏感配置。
- UI 自动化覆盖核心配置闭环和审计查询。
- WP2/WP3 模拟调用获取项目/应用/环境上下文、有效配置和写入审计。
- 回归数据初始化、清理和账号状态恢复。

退出标准：

- P0 接口自动化可在 CI 或测试环境稳定运行。
- UI 冒烟自动化覆盖基础配置闭环。
- 后续 WP 接入接口通过契约测试。
- 发布前无 P0/P1 阻塞缺陷。

## 14. 测试准入与准出建议

### 14.1 测试准入

- 需求、架构、接口契约、权限矩阵和审计事件清单已评审通过。
- 测试环境可用，数据库迁移脚本可重复执行。
- 基础账号、租户、项目、应用、环境种子数据可自动初始化。
- 后端提供统一 Trace ID，接口错误码和响应结构一致。
- 敏感配置测试使用专用假密钥，不使用真实生产凭证。

### 14.2 测试准出

- P0 功能用例通过率 100%。
- P0 接口自动化通过率 100%，无阻塞和高危安全缺陷。
- 多租户隔离、RBAC 越权、敏感信息脱敏、审计覆盖四类核心质量门禁全部通过。
- P1 缺陷有明确修复计划或业务接受说明。
- 自动化回归具备基础数据初始化和清理能力。

## 15. 总体建议

WP1 的测试重点不应停留在页面 CRUD，而应把“租户隔离、权限拒绝、停用即时生效、敏感值不泄露、审计可追踪”作为核心质量门禁。当前文档方向正确，足以进入测试方案和用例框架准备；但在权限矩阵、API 契约、状态流、敏感配置和审计清单冻结前，不建议启动大规模自动化脚本开发。

建议后续按 M0 至 M4 分阶段推进，先用接口自动化覆盖安全边界和控制面主链路，再用少量 UI 自动化验证管理后台的关键配置闭环。这样既能降低早期 UI 变动带来的维护成本，也能尽早建立 WP1 对后续工作包的自动化验证基础。
